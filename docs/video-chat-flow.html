01

Flow ทั้งหมด แบบ step-by-step

ทุก step ในเฟส B ทำงานแบบ synchronous อยู่ใน HTTP request เดียว — response จะไม่กลับจนกว่าจะครบทุกขั้น

PHASE A Chunked Upload — ดันไฟล์ video ขึ้น server ก่อน เกิด ก่อน ถึง route ที่ถาม · คนละ endpoint
1
เปิดงาน upload AppAPI ต่ำ

POST /multipart/initiate — สร้าง record ใน MongoDB (UploadMultiparts) แล้วคืน uploadId กลับไป ทำแค่ DB อย่างเดียว จึงเร็ว

2
ส่งไฟล์ทีละ chunk AppAPI สูงสุด

PUT /multipart/upload_part — client ตัดไฟล์เป็นก้อนแล้วส่งทีละก้อน (1 HTTP request ต่อ 1 chunk) การโอนทั้งไฟล์ผ่าน network คือเวลาที่ผู้ใช้รู้สึกนานที่สุด limit ต่อ upload สูงถึง 50 GB

↻ วนซ้ำจนครบทุก chunk · เรียงลำดับ
3
ประกอบไฟล์บน disk (synchronous) API สูง

ทุก chunk ที่เข้ามา server ใช้ fs.readFileSync + fs.appendFileSync + fs.unlinkSync ต่อไฟล์เข้าด้วยกัน และ fs.renameSync ตอน chunk สุดท้าย — เป็น sync call ที่ block Node event loop จึงหน่วงทั้งการ upload นี้และ request อื่น ๆ ที่วิ่งพร้อมกัน

PHASE B Publish — PUT /c2c/send/file_large route ที่โจทย์ชี้มา
4
รับ thumbnail + ตรวจสิทธิ์ AppAPI ต่ำ

uploadSingleFile (multer) รับแค่รูป thumbnail ไม่ใช่ตัว video — ตัว video ถูกดันขึ้นไปแล้วในเฟส A จากนั้น checkUploadId lookup MongoDB เพื่อหา record ไฟล์ที่ประกอบเสร็จแล้วบน disk

5
อัปโหลด video เต็มไฟล์ขึ้น COS APICOS สูง

uploadFileToCos อ่านไฟล์จาก disk แล้วส่งขึ้น Tencent COS แบบ multipart (SliceSize 5 MB) — เป็นการโอนไฟล์ใหญ่รอบที่สอง (server → COS) เวลาแปรตามขนาดไฟล์ และ request รอจนอัปเสร็จ

6
Probe metadata + trigger transcode APICI กลาง

getMediaInfo ยิงไปถาม Tencent CI ว่าไฟล์กว้างเท่าไร (network round-trip) ถ้า width > 1920 จะยิง triggerTranscodeJob สร้างงาน transcode เป็น FHD (template H264-MP4-ake) — แค่สั่งงานแล้วไปต่อ ไม่รอ transcode เสร็จ

7
อัป thumbnail + หาความยาว video APICOS กลาง

อัป thumbnail ขึ้น COS (ก้อนเล็ก) แล้ว getVideoDurationInSeconds รัน ffprobe บนไฟล์ video local เพื่อดึงความยาว — การ spawn process นี้มีต้นทุนคงที่ที่รู้สึกได้ ปิดท้ายด้วยเขียน log record ลง MongoDB

8
ส่งข้อความเข้า Tencent IM APIIM ต่ำ

sendC2CMsg → TencentServices.sendMsg POST ไปที่ REST API /openim/sendmsg พร้อม MsgBody (ชี้ไป video ต้นฉบับบน COS) และ cloudCustomData ที่แนบ URL ของไฟล์ FHD ที่กำลัง transcode

9
Cleanup + ตอบกลับ API ต่ำ

ลบ multipart record และลบ thumbnail temp บน disk แล้วจึงตอบ success กลับไปที่ app — จบ request

⚠️

Transcode ทำแบบ async — วิดีโอ FHD อาจยังเปิดไม่ได้ทันที

งาน transcode ถูก "สั่ง" แล้วปล่อยให้ Tencent CI ทำเบื้องหลัง โค้ดไม่ poll และไม่มี webhook มา reconcile ผู้รับจะเปิด video ต้นฉบับ (VideoUrl) ได้ทันที แต่ URL ไฟล์ FHD ใน cloudCustomData.VideoTranscode.url อาจ 404 อยู่ช่วงหนึ่งจนกว่า CI จะ transcode เสร็จ — นี่เป็นความล่าช้าที่ "มองไม่เห็น" ใน request แต่ผู้ใช้ปลายทางเจอ

02

จัดอันดับจุดหน่วง

เรียงตามผลกระทบต่อเวลารวม · "scale ตามขนาด" = ยิ่งไฟล์ใหญ่ยิ่งช้า, "คงที่" = ต้นทุนเกือบเท่าเดิมทุกไฟล์

#จุดเฟสประเภทความรุนแรง
1 Client → API ส่ง chunk ทั้งไฟล์ผ่าน network A scale ตามขนาด + bandwidth สูงสุด
2 ประกอบ chunk บน disk แบบ sync (block event loop) A scale ตามขนาด สูง
3 อัป video API → COS (multipart 5MB) B scale ตามขนาด สูง
4 getMediaInfo ถาม CI (network round-trip) B คงที่ กลาง
5 ffprobe หาความยาว video (spawn process) B คงที่ กลาง
6 อัป thumbnail COS + trigger transcode job B คงที่ ต่ำ
7 Tencent IM sendmsg B คงที่ ต่ำ
8 MongoDB writes / deletes A+B คงที่ ต่ำ
03

ข้อเสนอแนะสำหรับ dev

เรียงตามผลตอบแทนต่อความพยายาม — ตัดตัวการอันดับ 1–3 ก่อน

A

เลี่ยง double-hop: ให้ client อัปเข้า COS ตรง ๆ

ตอนนี้ไฟล์เดินทางสองรอบ — client→API (เฟส A) แล้ว API→COS (step 5) ถ้าใช้ pre-signed URL / COS multipart ฝั่ง client ให้ app อัปเข้า COS โดยตรง จะตัดทั้งการโอนรอบสอง, การประกอบไฟล์บน disk, และภาระ disk ของ server ออกได้พร้อมกัน (แก้อันดับ 1, 2, 3 ทีเดียว)

B

เปลี่ยน sync fs เป็น async / stream

ถ้ายังคงประกอบไฟล์บน server ให้เปลี่ยน readFileSync/appendFileSync เป็น stream (createWriteStream + pipe) เพื่อไม่ให้ block event loop — ลดผลกระทบที่ลามไปยัง request อื่นทั้งระบบ

C

Stream API → COS แทนอ่านทั้งไฟล์จาก disk

หากไฟล์อยู่ที่ COS อยู่แล้ว (ข้อ A) ก็ไม่ต้องอัปซ้ำเลย แต่ถ้ายังต้องผ่าน server ให้ stream ตรงจาก disk เข้า COS เพื่อลด peak memory และ latency

D

สื่อสาร transcode ที่ยังไม่พร้อมให้ผู้ใช้เข้าใจ

เพิ่ม callback/webhook จาก CI หรือให้ client fallback ไป VideoUrl ต้นฉบับ ระหว่างรอ FHD เพื่อไม่ให้ผู้รับเจอ video ที่ยังเปิดไม่ได้ (จุด "หน่วงที่มองไม่เห็น")
